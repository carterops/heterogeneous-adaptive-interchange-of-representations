# Full-stack quality loop: prospective paired trial

This post-v0.1.1 note records a bounded product/runtime experiment, including failed first attempts. It does not change the H-A-I-R public wire format or the authored v0.1.1 evaluation fixtures. Product code and the candidate orchestrator remain in their owning private workspaces.

## Question and method

Can an Astra runtime that carries a source-bound full-stack brief through native H-A-I-R messages, requires actual recipient acknowledgements and pre-build design critique, and routes independent backend/rendered findings for repair produce a better complete workflow than the installed runtime?

Two isolated tasks started from frozen, identical source copies within each product. The P&L Jobs task moved one synthetic two-date job from complete cost coverage to a higher source version with missing material cost, then to a restored version with a changed amount. It also required authenticated, CSRF-protected forecast/archive writes and stale-edit rejection. The Hearth task used fake browser observations and mocked OS capture to test Pause, browser unpair, Resume, a new pair, and a fresh observation. No live product or real capture was used. The current condition used installed Astra 3.0.1; the revised condition used an isolated 3.1.0 candidate. The revised candidate recorded real handoff, acknowledgement, and design-review events before implementation. First-attempt source and failures were retained before repair.

The requested agent model and effort matched across corresponding roles, but the host did not return provider-attested model identity or per-call billed cost. This is a paired task and source comparison, **not a controlled cost or model-quality result**. An earlier current-arm assignment was invalidated after unintended cross-condition information appeared before product editing; a separate harness run was invalidated after it restored a default local research ledger. A clean isolated current run was restarted and those invalid attempts remain in the private record.

## Observations

| Check | Current runtime condition | Revised runtime condition |
| --- | --- | --- |
| P&L first source attempt | **FAIL** hidden source-withdrawal check: the historical $10 material amount remained in current known cost ($60 rather than $50). | **PASS** exact complete→missing→restored financial probe, including missing profit/margin, source version/date, and scoped auth/CSRF/stale-write checks. Independent review then found separate **FAIL** cases: departing all source activity left the old job revision unchanged and admitted stale writes; a declared missing forecast could appear complete; the runtime build ID omitted financial/concurrency modules. |
| P&L first rendered result | Independent review found small targets and hard-to-read decision/source text. | Independent review found six hierarchy, contrast, target-size, stale-state, terminology and historical-line visibility defects despite correct real missing/restored figures. |
| P&L bounded repairs | One backend repair passed the exact hidden source transition; repaired visual workflow acceptance was not run. | Source-ownership revision, forecast-status, build-identity and source-scoped commercial-term repairs passed the saved eight-case audit and 23 native tests. The exact hidden HTTP source transition passed again on the final build. A UI repair passed 27 real-source desktop/tablet/mobile captures; independent visual re-review passed its six previously failed criteria. These scoped checks do not constitute a human task result. |
| Hearth permission sequence | The clean synthetic sequence passed after a shared evaluator amendment; independent deferred-context review found revoked browser context could still reach a queued model call. | The same sequence passed. Independent review also found an old pending command could survive unpair/re-pair and a research-pool compatibility failure. These were repaired and passed scoped retests. |
| Hearth deferred semantic context | Round-one selected-context repair passed its two original cases, but a shared three-case probe found two failures in queued semantic browser context. Round two passed that probe independently (3/3) and 46 relevant native tests. | The shared semantic probe passed 3/3 after repair, with earlier first-pass failures preserved. Its real extension lifecycle, real OS capture and full native regression suite remain unverified. |

A further independent P&L review found a **cross-source job-number collision**: two jobs with the same display number could not be edited reliably, and a keyed forecast save still changed both jobs' displayed forecast. A separate current-condition in-memory check also changed both jobs through its number-scoped commercial-terms path. The underlying collision therefore appears in both conditions; the exact write entrypoints differ. A revised-condition repair now keys manual terms to the selected operational job; the saved synthetic repro shows an ambiguous number-only write rejected without mutation and a keyed write changing only its target. Independent re-review then found a second legacy-data inconsistency after a duplicate job departed: the Jobs projection restored an unscoped forecast that the detailed terms API still marked ambiguous. A further repair makes those views agree, including when the duplicate arrives and departs without an intervening Jobs read. The independent scoped rereview passed; broader compatibility and rollback remain open.

One real first-pass local P&L restoration reached the rendered screen in 1,605 ms against a selected 3,000 ms threshold. That is one observation, not a latency distribution. The repaired 27-view P&L capture set used an earlier backend build; the final build passed an exact HTTP financial transition and a narrower read-only desktop/mobile smoke check, not a complete combined interaction workflow. The Hearth counts and P&L checks are scoped synthetic/software results, not general usability scores. The revised runtime's live event chain passed integrity verification, while its promotion check remained false with open findings and unrun checkpoints; chain integrity does not prove the product is good.

## Current interpretation

The prospective trial supplies a useful mechanism and several concrete catches: acknowledgement/design review occurred before the revised build, and independent review exposed defects that the exact hidden probe and native tests missed. It **does not establish a cross-project quality advantage or justify promotion**. The final P&L architecture contract passed local structural and source-bound checks, but the independent visual pass is scoped; complete Hearth regression, external consumer compatibility, full database rollback, older ambiguous records, broader write authorization, blinded human answer-finding, actual billed cost and returned model identity are incomplete or unknown. First-pass quality and repaired quality remain separate. The next evaluation must resolve those boundaries and repeat the paired comparison without treating a test pass as semantic or product-quality proof.
